## 1. 定位

### 1.1 一句话

**驻班 AI 教研员**：看得懂全校考试数据、记得住每个班的追踪历史、能落笔成文，产出物一律经教师签发才对外。

### 1.2 替教师完成的三件工作

| # | 痛点 | 现状 | 本产品 |
|---|---|---|---|
| W1 | 看完报表后的「所以呢？」——数据显示 P2 跌了，原因是什么、该做什么 | 报告罗列行动行，无研判串联（diagnosis-sheet-redesign §0 P2/P4） | Agent 现场调查（顺前置链追根因、查教学进度佐证），给出带依据的判断与顺序化建议 |
| W2 | 文书负担——诊断单、家长材料、评语 | LLM 生成层已设计（诊断单重构 §②），但触发与修订仍是表单流程 | Agent 起草 → 教师改两个字 → 签发，全程对话式修订 |
| W3 | 追不了账——上次的干预做了没、有没有效 | 干预闭环设计已定稿但无持续跟踪者 | 班级维度的持久记忆（rollout 线程）：Agent 记得三次考试前说过什么、承诺过什么，主动对账 |

### 1.3 为什么 sc 是合适的坯子（而不是从零做）

市面上领域 Agent 的头号死因：让模型直接算数字 → 幻觉 → 产品信誉崩塌。sc 的四大不变量恰好是完整疫苗：

- 分析只读已提交数据；
- derive-on-read，派生状态不落库；
- LLM 输出过闸门（`app/llm/gateway.py`，熔断/校验/降级）;
- 报告数字零幻觉（模板槽位注入，`NARRATIVE_SYSTEM` 铁律）。

**可信的计算内核已建成且经 127+ 测试验证**，缺的只是外面那层「自己决定下一步做什么」的编排。Agent 化是把既有资产叠加一层，不是重写。

## 2. 总体架构

```
┌─ 校内服务器（一台盒子，docker-compose）────────────────────────────┐
│                                                                    │
│  nginx ──► Vue 前端（静态文件；含对话面板/任务卡片/审批收件箱）      │
│        ├─► sc Python 后端（FastAPI，「脑」，现状不动）               │
│        │      ├─ 确定性管线：KB/追踪/归因/报告渲染                   │
│        │      └─ 新增：MCP Server 进程（把领域能力暴露为工具）       │
│        ├─► 会话网关（新增，Python/FastAPI）                          │
│        │      · 浏览器 WebSocket/SSE ⇄ JSON-RPC 双向翻译            │
│        │      · 教师鉴权与会话↔线程绑定                              │
│        │      · 任务触发器入口（摄取完成 → 拉起分析 Task）           │
│        └─► codex 魔改壳（Rust，「运行时」）                           │
│               · Task/Turn 循环 · rollout 会话落盘 · 审批门           │
│               · 工具调用 ──MCP──► sc 的 MCP Server                   │
│               · LLM 调用 ──HTTPS──► 学校自选模型 API                 │
│  SQLite(WAL) 数据卷 + rollout 文件卷 + 定时备份                      │
└──────────────┬──────────────────────────┬──────────────────────────┘
   入站：校园网内（浏览器/手机扫码）        出站仅两条 HTTPS：
                                          ① LLM API  ② 钉钉 Stream 长连接
```

三条腿各司其职：

| 腿 | 技术 | 改动性质 |
|---|---|---|
| 壳（运行时） | codex 魔改（Rust） | 锚定 tag 后定向修改，diff 收拢于 §6 清单 |
| 脑（领域内核） | sc 后端（Python/FastAPI） | **业务代码零改动**；仅新增 `app/mcp_server.py` 入口与少量挂点 |
| 面（客户端） | Vue 3（现工作台演进） | 渐进增强，存量页面全部保留 |

**为什么脑不搬进壳里**：四大不变量、知识图谱建模、熔断/审计基建全在几万行 Python 里，移植进 Rust 等于烧掉最值钱的资产并重新证明正确性。MCP 是两者之间现成的标准接口——壳原生支持 MCP client（rmcp-client），sc 加一个 MCP Server 进程即可，双向都是加法不是手术。

**为什么需要会话网关**（诚实的技术注记）：codex app-server 的传输面是 stdio（默认）/ unix socket / websocket（**experimental，官方标注 unsupported**）。浏览器无法直接说 stdio，生产也不宜押注实验性 ws 传输，因此需要一个自建的轻量翻译层：对上是浏览器友好的 WebSocket/SSE + 鉴权，对下是壳的标准输入输出。网关同时承担 §5.4 触发器和 §5.5 身份注入两个职责，**它是壳外的独立组件，不为它改一行壳的源码**。

### 2.1 仓库布局（2026-08-24 敲定，D9）

产品为**单仓（monorepo）五目录**。理由：§8.3 已定「三组件同版本号打包发布」，单仓让发版 = 给仓库打一个 tag；拆多仓则每次发布要对齐三个仓库的 tag，纯手工仪式无收益（单人开发 + 版本锁步 + 一份 compose，三个条件全指向单仓）。

```
sc/                        # 产品仓库 = fork 本体（D7 定名后可整体改名）
├── backend/               # 脑：sc 确定性内核 —— 目录名与位置永不动，将来只加 mcp_server.py 入口
├── runtime/               # 壳：魔改 codex —— Phase 0 结束时整体收编（见下三条铁律）
│   ├── codex-rs/…         #   内部结构保持上游原样，一个文件都不重排
│   ├── Cargo.toml         #   workspace 根原样保留；新 crate 以新增成员进入
│   └── handbook → 仓库根  #   工程文档放产品仓库根（见 §6.6），不放 runtime/ 内
├── gateway/               # 网：会话网关（Python/FastAPI）—— Phase 0 网关雏形直接落位于此
├── frontend/              # 面：Vue 工作台 —— 不动
├── design-system/         # 不动
├── deploy/
│   └── docker-compose.yml # 部署编排（已从根目录迁入；build/env_file 相对路径已修正）
├── docs/                  # 产品设计文档（现有文化不变）
├── handbook/              # 壳的工程文档五件套（§6.6）—— 放产品仓库根，单一归属
└── README / DEPLOY / LICENSE / NOTICE / .github 照旧
```

`runtime/` 收编三条铁律：

1. **去 `.git` 整体搬入，内部一字不动**。cherry-pick 的补丁按路径应用，每挪动一个上游文件 = 将来每一笔 cherry-pick 多一处手工对位。我们的改动全部以新增 workspace 成员方式进入（`edu-tools` / `school-authz`），存量路径零分歧——「基底一次性捐赠」的字面执行：先整棵树原样供起来，再动刀；
2. **目录名用功能位命名**（`runtime/` `gateway/` `backend/`），不绑品牌词——D7 定名时只改 crate 前缀与界面品牌，目录不动。「脑」是概念映射不是目录名，backend/ 永不改名；
3. **cherry-pick 跨仓配方**：vendor 后与上游无共同历史且路径带 `runtime/` 前缀，不能直接 cherry-pick。标准姿势：上游克隆 `git format-patch` 出补丁 → 本仓库 `git am --directory=runtime` 应用。此配方写入 AGENTS-FORK.md。

现有根目录 `codex/` 参考克隆的生命周期 = **Phase 0 用完即删**（D10）：其价值（精读材料产出 ARCHITECTURE.md v0 + 锚定来源）在 vendor 时耗尽。后续想再看上游参考的三个途径：① 直接看 GitHub 上游对应 tag（锚点 hash 已记 DELTA.md）；② 需要本地 grep 时临时克隆到仓库外任意位置（如 `~/refs/codex`）；③ 需要跑上游测试对比行为时按锚点 hash 克隆。附带收益：本仓库 .codegraph 索引不再吞 146 万行参考代码（当前 624MB 相当部分源于此）。

## 3. 概念映射

| codex 概念 | 本产品对应物 | 说明 |
|---|---|---|
| Op / SQ ← → EventMsg / EQ | 教师消息 / 网关下行事件流 | 协议即边界，原样继承 |
| Task（一次输入触发的完整工作） | 一次教师请求 或 一次考后自动分析 | 两类发起方式，见 §5.4 |
| Turn（一轮调用+工具执行） | 模型提议调一个 sc 工具 → 引擎执行 → 结果回喂 | 数字永远来自工具返回值 |
| 工具 registry/router | **五层流水线整体变成工具箱** | 每个 sc 能力 = 一个 MCP tool 定义 |
| rollout（JSONL append-only） | 班级维度持久记忆 + 全程可回放 | `llm_call_log` 是其雏形，扩展见 §5.6 |
| AskForApproval 审批 | 草稿签发门（§5.3） | 「允许执行命令？」→「签发这份诊断单？」 |
| execpolicy 规则 | 工具白名单 + 参数校验（edu-tools crate） | 内部函数调用，无需 OS 级沙箱——比 codex 简单得多 |
| 上下文硬预算（10K token P0 军规） | 工具分页取数代替整篇投喂 | 现 narrate 全文投喂模式退役为保底 |
| compaction 自动压缩 | 长会话历史摘要化 | 直接复用壳的 compact 机制 |
| SessionSource / originator | teacher_id + class_id 注入 ThreadConfigSnapshot | 多教师并发的身份载体 |

## 4. 产品形态

三层一体，按采纳成本排序：

### 4.1 第一层 · 任务卡片（被动入口）

考试数据摄取完成 → 系统自动发起该班的分析 Task → 教师打开工作台看到的不是空对话框，而是：

> 「周日 22:14 完成初二(3)班期中分析 · 2 个发现待查看」

教师不需要学会提问，成果送上门。卡片点击展开草稿（§4.3 的产出物）。

### 4.2 第二层 · 对话调查面板（能力纵深）

任何一份数据旁都可追问：「三班为什么弱？」「和月考比呢？」「下周搞限时训练涉及多少人？」。Agent 用只读工具现场调查，**每句结论旁挂「依据」链接**，点开就是确定性管线的原始数字——零幻觉不变量变成可见的 UI 元素，也是面向家长/校长展示可信度的卖点。

### 4.3 第三层 · 审批收件箱（权力结构）

一切对外产出物（班级诊断单正文、学生改进单、家长信、干预建议）均为 `draft` 状态进入收件箱；教师修订后点「签发」才生效。签发动作就是审批门（§5.3）。

### 4.4 场景走查（验收基准故事）

> 周五李老师拍完全班卷子上传。周一早读前打开工作台，一张卡片：「周日 22:14 完成期中分析」。点开草稿：班级诊断单的数字部分全部来自系统计算；下方是 Agent 的调查记录——它注意到 P3 从 62% 跌到 41%，沿前置链查到根因在 P2，又查教学进度确认 P2 刚讲完一周，于是写下判断：「不是应用能力退化，是新授未巩固，建议两周内限时巩固训练而非重讲。」李老师改了两个措辞，点签发。顺手问一句：「限时训练大概涉及多少人？」Agent 查名单：「18 人，明细如下。」

这个故事里每个要素都有对应机制：自动分析=§5.4 触发器；数字可信=脑的不变量；根因调查=只读工具链；落笔=LLM 生成层；签发=审批门；追问人数=只读工具。

### 4.5 明确不做（边界声明）

- **不建学生/家长门户**（沿用 intervention-loop-design 评审结论①：G11 落地前不引入新角色；本文落地后是否开放另议）；
- Agent **不触碰采集流程**（拍照识别/录入仍走既有表单流水线，Agent 只消费采集结果）；
- 建议**只覆盖知识维度的学法与教学安排**，不涉及动机、情绪、家庭归因（沿用干预闭环边界声明，写进壳的人格 prompt）；
- 数值层零 LLM 不动摇：Agent 写的是「研判与落笔」，一切数字由工具注入。

## 5. 关键机制设计

### 5.1 工具面（sc → MCP）

新增 `backend/app/mcp_server.py`（独立进程入口，基于 MCP Python SDK），把既有能力注册为工具。一期清单：

**只读工具（Phase 2 即接）**

| 工具名 | 背后能力 | 返回口径 |
|---|---|---|
| `get_class_overview` | 工作台聚合（Overview 数据源） | 班级级统计，学生仅别名 |
| `get_exam_summary` | 质量 snapshot_json（含 question_rates/common_weak） | 单场考试事实 |
| `get_kp_mastery` | mastery 推导（支持 as_of 时点） | 掌握度矩阵，分页 |
| `run_attribution` | 归因引擎（derive-on-read 实时推导） | 归因类型 + 根源点 + 置信依据 |
| `get_kp_detail` | 知识点 + 前置链（KpRelation 图查询） | 结构事实 |
| `get_teaching_progress` | TeachingProgress | 教过没、何时教的 |
| `list_students` | 名册（别名、分页） | 追问名单用 |

**写操作工具（Phase 3，过审批门）**

| 工具名 | 背后能力 | 门 |
|---|---|---|
| `create_report_draft` | 诊断单渲染（模板槽位）+ LLM 正文（诊断单重构 §2 规则） | 产出 draft，入收件箱 |
| `record_intervention` | 干预记录写入（干预闭环 §3） | draft → 教师确认 |

工具约束：参数强校验（school/class 越界一律拒绝）；返回一律 `name_or_alias` 不含真名（§9）；大结果集强制分页（上下文硬预算军规的落地）；每个工具响应携带 `_provenance`（来源端点+参数哈希），供前端「依据」链接回溯。

### 5.2 人格与 prompt（壳的基础指令替换）

替换 codex 全部编码类基础 prompt 为教育分析师版本，行为准则（将随试点迭代，prompt 版本化管理沿用 `NARRATIVE_PROMPT_VERSION` 文化）：

1. 只引用工具返回的数字；没有数据就明说不知道，禁止推算；
2. 结论必附依据（哪次考试、哪个工具结果）；
3. 成长框架措辞（项目既有文案文化的延续）；
4. 不越界（§4.5 第三条原文写入）；
5. 中文输出，篇幅克制（教师没时间读长文）。

### 5.3 审批门与草稿流

- 壳的审批框架保留，默认策略映射为：只读工具自动放行；写工具产生 draft 并暂停等待；**签发动作由教师在收件箱完成**（人在环上，且签发本身不消耗 Agent 循环）；
- 存储方案：复用 `Report` 表新增 `status` 列（`draft | issued | archived`），走既有 idempotent ALTER 增量机制，产物保持单一来源；
- 收件箱 = 前端新面板（工作台导航新增「待签发」角标），列表项显示草稿类型/班级/时间/差异预览，行内签发或打回。

### 5.4 任务触发器（codex 里不存在、需要新建的组件）

两类 Task 发起：

- **交互式**：教师消息 → 网关 → 绑定班级线程提交 TurnInput（壳原生路径）；
- **触发式**（新建）：sc 摄取完成事件（batch job success 回调点）→ 网关内部接口 → 在该班持久线程上拉起「考后分析」Task。分析 prompt 由**版本化的任务模板**生成（如 `POST_EXAM_ANALYSIS_V1`），产出草稿入收件箱。

触发器活在网关里，壳只需暴露「在指定线程上发起任务」的既有接口——零核改。

### 5.5 鉴权与身份传播（G11 在此落地）

- 教师登录（一期：管理员建账号 + 口令；二期可换钉钉 OAuth）→ 网关签发会话 token；
- 网关为每位教师的会话绑定**专属班级线程集合**（教师↔班多对多关系来自现有 org 模型）；
- 工具调用身份传播两条路，按实施代价取舍：
  - **首选**：每线程独立的 MCP 连接注入 `X-Teacher-Token` 头 → sc MCP Server 校验后做班级级过滤（可能需要对壳的 MCP 配置做小补丁，属 §6「加」的范围）；
  - **兜底**：身份作为显式工具参数传递，MCP Server 强制校验（零核改，先跑通）；
- sc 后端所有分析端点补齐 `teacher↔class` 归属校验（这是 G11 的本体工作，与 Agent 化共用一套实现）；
- 单校部署消解了跨租户隔离问题——权限粒度到「校内教师↔班级」即止。

### 5.6 记忆与 rollout

- 粒度：**一班一线程**（跨学期滚动），而非一会话一线程——W3「追账」能力要求 Agent 记得班级历史；教师个人的临时问答开 ephemeral 线程不落重要记忆；
- 落盘：壳的 rollout 机制原样使用（JSONL + state_db），存校内卷；
- PII：工具返回已最小化（别名制），rollout 天然不含真名；保留期限策略见 §9；
- 与 `llm_call_log` 的关系升级：审计表从「LLM 调用记录」扩展为用量台账（§5.8），rollout 管「对话内容可回放」，分工清晰。

### 5.7 成本与预算护栏（第一天就有）

| 闸 | 默认值（试点期实测后修订） | 超限行为 |
|---|---|---|
| 单 Task 轮数上限 | 12 轮 | 优雅收尾：已完成调查照常呈现 + 标注「分析中断」 |
| 单 Task token 预算 | ~200K tokens | 同上 |
| 月度软限额 | 可配置，80% 时通知管理员 | 仅提醒不断供；硬限额开关留给学校 |

### 5.8 降级协议（熔断语义重定义）

现状：单发调用失败静默降级返回空串（不变量③）。Agent 循环下一个 Task 可能含十几次 LLM 调用，语义升级为 **Task 级检查点**：

- 已完成的工具调用与中间结论都在 rollout 里，天然是检查点；
- 第 k 轮熔断 → Task 标记 `interrupted(breaker_open)`，已完成部分作为草稿入收件箱并明确标注；
- 熔断恢复（half-open 成功）后，教师可一键「继续分析」——从 rollout 断点续跑；
- 兜底不变量③延伸：即使 Agent 全程不可用，确定性管线与纯模板报告照常出——**LLM 断供降低体验，不降低可用性**。

### 5.9 用量台账（llm_call_log 扩展 + 管理面板）

- `llm_call_log` 增加 `prompt_tokens`、`completion_tokens` 两列（ALTER 增量；mock 路径记 0）；
- `task` 字段新增取值：`agent_turn`（循环内调用）、`post_exam_analysis`（触发式任务）等；
- 管理端新页「本月消耗」：按 task/日 聚合的 token 与调用数——学校自己付钱，就必须看得见花在哪（§8 商业模式的信任基建）。

### 5.10 模型接入

- 壳的 model-provider 抽象原生支持 OpenAI 兼容端点，学校 key 填在管理设置页（加密落库）；
- 开通向导列主流国产模型的申请步骤（推荐序列见【D5】）；
- 本地逃生舱：compose 提供 `--profile offline` 起 Ollama，同一台盒子全离线运行（质量打折但数据绝不出校），作为销售选项而非默认；
- 诚实注记：壳的 response_id 书签续传与远程压缩以 OpenAI Responses API 为前提，国产兼容端点走 Chat 兼容层时这两项能力降级为本地实现——刀口在 `model-provider`/`client.rs`/compact 系列，属 §6「换」的范围，Phase 1 处理。

## 6. 魔改清单（diff 收拢原则）

总原则：**别人 diff 我们的仓库时，90% 改动集中在十几个能一口气讲完的位置**。两级策略——能用扩展点的绝不进 core；必须改源的集中进新 crate。

### 6.1 删（Phase 1 裁剪，110+ crates → 约 30）

cloud-tasks 全家、realtime 全家、code-mode/v8 全家、connectors、TUI（我们唯一的前门是 app-server）、exec 人类输出面、apply_patch 默认工具、编码类 prompt 文件、linux-sandbox/windows-sandbox（内部函数调用无需 OS 沙箱；保留依赖评估后决定是否连带删除）。

### 6.2 换

| 位置 | 内容 |
|---|---|
| 基础 system prompt | → §5.2 教育分析师人格 |
| 默认工具面 | shell/apply_patch/web_search 退场 → MCP 白名单 |
| 默认审批策略 | → §5.3 映射 |
| compact 远程路径 | → 本地实现（国产端点） |

### 6.3 加（新 crate，集中放）

| crate | 职责 |
|---|---|
| `edu-tools` | 领域工具参数校验、白名单、`_provenance` 注入 |
| `school-authz` | 教师↔班级权限断言、token 校验、身份注入 MCP 连接 |

配置默认值改造（rollout 最小化、预算闸默认值、中文 locale）随两 crate 走。

### 6.4 不动（动了就是负债）

SQ/EQ 协议、CodexThread/Session/Task/Turn 循环、rollout recorder 与压缩、审批框架本体、熔断重试（responses_retry）、hooks 机制。

### 6.5 工程纪律（沿承 codex AGENTS.md，裁剪为本仓库版）

锚定 tag 军规：基底一次性捐赠，上游安全修复 cherry-pick、永不整体合并；模块 <500 行；非机械变更 ≤800 行；新 trait 必须有契约文档。合规底线：保留 Apache-2.0 LICENSE 与 NOTICE 归属；去除 Codex 商标名（产品命名见【D7】）。

### 6.6 文档基建（handbook/，fork 自己的工程文档）

问题（2026-08-24 确认）：codex 仓内文档写给上游贡献者，撑不起魔改基底——根目录 `docs/` 大量条目是「详见 developers.openai.com」的外链占位（sandbox/exec/skills/config 等），在线内容随上游 main 漂移；仓内技术文档仅 `protocol_v1.md`（自认与代码可能有出入）、`bazel.md`、`codex_mcp_interface.md` 与零星 crate README，110+ crates 无分类地图；「如何安全删除一个 crate」「双构建系统同步义务」等魔改必需知识散落在 AGENTS.md 规则中。**锚定之后上游文档即失联**，必须自建 fork 层文档。

方案：魔改仓库新建顶层 `handbook/` 目录（**位置已按 §2.1 定为产品仓库根，与上游 `docs/` 物理隔离，最小化 cherry-pick 冲突面；AGENTS-FORK / BUILD 两篇天然覆盖全产品，工程文档单一归属**），五件套：

| 文档 | 内容 | 产生时机 |
|---|---|---|
| `ARCHITECTURE.md` | 以锚定 commit 为准的真实架构：crate 分组分类表 + 三条关键数据流（提交→Turn 循环→工具分派→事件流；rollout 追加路径；审批流），断言一律附文件路径引用 | Phase 0 精读产出 v0 |
| `CRATES.md` | crate 花名册：保留 crate 逐个一行职责说明 + 删除清单附理由——§6.1 裁剪的执行账本 | 随裁剪实时记账 |
| `DELTA.md` | 相对锚点的全部源码分歧台账（位置/内容/原因），ADR 条目式；头部记录锚定 commit | 第一笔源码修改起开账 |
| `BUILD.md` | 构建/测试/发布指南 + 平台支持矩阵声明（生产 = linux/docker，开发 = macOS）；**Cargo + Bazel 双轨操作义务**（D8 已定：保留双轨） | Phase 1 |
| `AGENTS-FORK.md` | fork 自己的工程纪律：自上游 AGENTS.md 裁剪（去 TUI/编码特定条目）+ handbook 维护规则 | Phase 1 |

配套纪律两条：① **文档随码走**——任何行为变更必须在同一 PR 更新 handbook 对应文档；② **对账机制**——每批 cherry-pick 合入后，抽查 ARCHITECTURE.md / DELTA.md 中的文件路径引用是否仍成立，失效即修。

双轨构建义务（随 D8 固化）：新增 crate（`edu-tools` / `school-authz`）必须同步提供 `BUILD.bazel`；改动 Rust 依赖（Cargo.toml/Cargo.lock）后必须运行 `just bazel-lock-update` 并将 `MODULE.bazel.lock` 更新纳入同一变更；fork CI 保留 Bazel 侧 lockfile 漂移检查；cherry-pick 上游修复时其 BUILD.bazel 变更照常合入，不得只挑 Cargo 半边。cherry-pick 的跨仓应用配方（format-patch + `git am --directory=runtime`）见 §2.1 铁律三。

## 8. 部署形态：一校一盒

### 8.1 拓扑与规模感

一台校内机器（4C8G 足够；NUC/迷你主机或百元月 VPS）跑全套 compose。几十个教师、SQLite WAL、Agent 是编排不是算力大户——单校粒度绰绰有余。硬件门槛低到「任何能装 Docker 的盒子」，这是私有化叙事成立的物理基础。

### 8.2 网络立场

**入站基本不可能，出站精打细算**：入站只有校园网内的浏览器访问；出站仅 LLM API 与钉钉 Stream 两条 HTTPS。运维、升级、监控全部不依赖反向入站。

### 8.3 装机与升级生命周期

- **试点期（1~3 校）**：手动即最优。安装体验收敛为一句话：拷 `docker-compose.yml` + `.env`（学校标识/LLM key/管理员账号三项），`docker compose up -d`。首开通 30 分钟向导：建 KB → 建班 → 导名册 → 拍第一份卷子。现有基建（init_db 双轨、/ready、备份脚本、DEPLOY.md）直接复用，新增动作只有把网关与壳加进 compose；
- **规模期（10+ 校）**：镜像仓库（阿里云个人版免费）+ 三组件**同版本号打包发布**（防漂移）+ watchtower 类定时拉取；每盒每日一次出站心跳向你汇报版本//ready 结果/磁盘水位（用户开口前知道谁挂了）；
- **回滚** = 保留上一版镜像 tag 一条命令退回；DB 迁移走既有双轨机制。

### 8.4 模型消费归属

**学校自持 key、自担消费**（2026-08-24 敲定）。由此产生的三个必做项已在 §5.1/§5.9/§5.7 落实：开通向导、用量台账、预算护栏。量级判断：单次班级分析任务约数万至二十万 token，国产模型定价下为毛钱级；一学年重度使用百元级——销售话术可以直说「模型费用一年不到一顿工作餐」（试点实测后写入材料）。

## 12. 决策记录（本次讨论已定，2026-08-24）

1. **路线定性**：基于 codex 源码魔改做教育垂直 Agent 产品（非 fork 跟随、非纯借鉴重写）；sc 后端整体为领域内核不迁移；
2. **合规路径**：Apache-2.0 允许闭源商用魔改；保留 LICENSE/NOTICE、去除 Codex 商标；
3. **军规**：锚定 tag、cherry-pick 安全补丁、永不整体合并上游；
4. **架构**：壳（Rust 魔改）/ 脑（sc Python 不动，MCP 包装）/ 面（Vue 演进）三条腿 + 自建会话网关（浏览器⇄stdio 翻译、鉴权、触发器）；
5. **产品形态**：任务卡片 + 对话调查面板（结论附依据链接）+ 审批收件箱；一班一线程持久记忆；四条不做边界（§4.5）；
6. **客户端**：Web 服务端为中心，PWA 观感，钉钉先行，Tauri 可选，不做原生 App；
7. **部署**：一校一盒 compose 私有化，出站-only 网络；试点手动装机、规模期镜像分发+心跳；
8. **商业模式**：软件部署授权归我方，模型消费学校自持 key 自担；配套向导+用量台账+护栏三件套。

以下为 D1–D8 敲定记录（2026-08-24，用户确认按文档倾向执行）：

9. **【D1】MVP 第一闭环 = A**：上传→自动分析→签发诊断单（触发器 + 收件箱先行）；对话调查面板随后补齐。Phase 2 排序据此执行；
